Dash is configured through **Mission Control**. There are no config files to hand-edit — you deploy agents, connect providers, and set up messaging apps from the desktop app, and Mission Control saves everything for you.

This page explains what you can configure, where Dash stores its data, and the few environment variables and CLI flags available when you run the gateway on its own.

## Agent settings

Each agent is configured in Mission Control's **Deploy** wizard (and editable later from the agent's **Configuration** tab). An agent has these settings:

| Setting | Required | Description |
|---------|----------|-------------|
| Model | yes | The model the agent uses, in `provider/model` format (e.g. `anthropic/claude-sonnet-4-20250514`). The dropdown is populated live from the providers you've connected. See [AI Providers](/ai-providers). |
| System prompt | yes | Instructions sent with every request that shape the agent's behavior. |
| Tools | no | Which capabilities the agent can use. See [Tools](/tools) for the full list. |
| Max tokens | no | Maximum response length in tokens (default: `4096`). |
| Working directory | no | Where the agent's file and shell tools operate. Defaults to `~/.dash/workspaces/<agent-id>`. |
| Fallback models | no | Backup models to try if the primary model is unavailable. See [Agents](/agents#fallback-models). |
| Extended thinking | no | Let the model reason before responding. See [Extended thinking](/extended-thinking). |
| Skills | no | Reusable instructions the agent can discover and load. See [Skills](/skills). |

Your agents are saved to `~/.dash/gateway/agents.json` and restored automatically when the gateway restarts.

## Swarm

An agent can be given a **swarm** so it can spawn short-lived **worker** subagents that run in parallel, each with its own isolated context, and then synthesize their reports into one answer. Swarm is **off by default** and is enabled per agent from Mission Control's **Configuration** tab → **Swarm** card ("Enable swarm — let this agent spawn parallel workers"). When it's on, the agent gains the `spawn_worker`, `wait_workers`, `send_to_worker`, and `check_workers` tools — see [Tools → Swarm orchestration](/tools#swarm-orchestration).

Every agent carries its own optional swarm block on its config (saved verbatim to `agents.json`):

| Setting | Default | Description |
|---------|---------|-------------|
| `enabled` | `false` | Whether this agent may spawn workers at all. When off, the swarm tools are not given to the agent. |
| `maxConcurrentWorkers` | `8` | Most workers this agent may run **at once** in a single turn. |
| `maxWorkersPerRun` | `24` | Most workers this agent may spawn **in total** across one turn. |
| `maxSteersPerWorker` | `10` | Most follow-up messages (steers/answers) the orchestrator may send to any one worker. |
| `maxRunSeconds` | `1800` | Wall-clock limit for a single swarm turn (30 minutes). When it's hit, the turn closes and in-flight workers are settled. |
| `allowedModels` | *(unset)* | Optional list of models a worker may use. When unset, workers use the orchestrator's own model (and its fallbacks). |

Leave any cap **blank** to inherit the gateway default (below). A cap change **takes effect on the agent's next message** — the gateway rebuilds the agent so the new limits and the enabled/disabled state apply to the next turn.

### Gateway swarm defaults

The gateway also enforces a **global** ceiling across every agent's runs and supplies the per-agent defaults above. Each one can be overridden with an environment variable set where the gateway runs:

| Setting | Default | Environment variable | Description |
|---------|---------|----------------------|-------------|
| `maxConcurrentWorkersGlobal` | `16` | `SWARM_MAX_CONCURRENT_WORKERS_GLOBAL` | Hard ceiling on workers running **at once across all agents** on this gateway. A spawn that would exceed it fails until other workers finish. |
| `defaults.maxConcurrentWorkers` | `8` | `SWARM_DEFAULT_MAX_CONCURRENT_WORKERS` | Per-agent default used when an agent's own `maxConcurrentWorkers` is blank. |
| `defaults.maxWorkersPerRun` | `24` | `SWARM_DEFAULT_MAX_WORKERS_PER_RUN` | Per-agent default for `maxWorkersPerRun`. |
| `defaults.maxSteersPerWorker` | `10` | `SWARM_DEFAULT_MAX_STEERS_PER_WORKER` | Per-agent default for `maxSteersPerWorker`. |
| `defaults.maxRunSeconds` | `1800` | `SWARM_DEFAULT_MAX_RUN_SECONDS` | Per-agent default for `maxRunSeconds`. |

Values must be **positive whole numbers** — anything else is ignored with a warning in the gateway log, and the built-in default is used instead. When Mission Control manages the gateway for you, set the variable in the environment you launch Mission Control from — the gateway inherits it. Restart the gateway (or Mission Control) to apply a change.

Worker transcripts are written under `~/.dash/gateway/sessions/<agent-name>/.swarm/` and are never auto-deleted — see [Troubleshooting](/troubleshooting#swarm) if you need to find or clean them up.

## Data directory

Everything Dash stores on disk lives under a single root — `~/.dash` by default — organized into clearly named subfolders:

```
~/.dash/
├── gateway/      # gateway data: credentials, agents, sessions, skills, databases
├── desktop/      # Mission Control app data: settings, conversations
├── logs/         # mc.log and gateway.log
└── workspaces/   # one folder per agent (where its files live)
```

This is the same location whether you launch Dash through Mission Control or run the gateway on its own, so your agents, credentials, and conversations are always in one predictable place. You can open any of these folders in Finder or your editor.

Two of these subfolders are **data directories** in their own right — each is the root a single component reads and writes:

- The **gateway's** data directory is `~/.dash/gateway` (credentials, agents, sessions, skills, databases, and plugins).
- **Mission Control's** data directory is `~/.dash/desktop` (app settings and conversations).

Where this page writes `<dataDir>` as a placeholder — for example throughout [Plugins](#plugins) — it always means the **gateway's** data directory, `~/.dash/gateway`, since the gateway is the component that loads those files.

To store everything somewhere else (for example, a separate disk or multiple profiles), set `DASH_HOME` to a directory of your choosing. Running the gateway with `--data-dir <path>` overrides just the gateway's own folder; `MC_DATA_DIR` overrides just Mission Control's.

<Note>
  Upgrading from an older version? The first time Dash starts, it automatically moves your existing data into `~/.dash` — no action needed. See [Troubleshooting](/troubleshooting#my-data-moved-after-updating) if anything looks missing.
</Note>

## Environment variables

Dash needs no environment variables for normal Mission Control use. These are available for advanced and standalone scenarios:

| Variable | Description |
|----------|-------------|
| `DASH_HOME` | Root directory for everything Dash stores on disk (default: `~/.dash`). |
| `MC_DATA_DIR` | Override just the Mission Control app's data folder (used by tests and QA). |
| `POOL_MAX_SIZE` | Maximum number of agent runtimes kept in memory by the gateway (default: `200`). |
| `SWARM_MAX_CONCURRENT_WORKERS_GLOBAL` | Ceiling on swarm workers running at once across **all** agents (default: `16`). |
| `SWARM_DEFAULT_*` | Per-agent swarm cap defaults — see [Gateway swarm defaults](#gateway-swarm-defaults) for the full list. |
| `NODE_ENV` | Set to `production` to quiet the gateway's verbose request logging. |

Provider API keys are **not** read from environment variables when you use Mission Control — they live in the encrypted credential store (see [Secrets](/secrets)). When running the gateway standalone, you can supply them as environment variables (e.g. `ANTHROPIC_API_KEY`); see [AI Providers](/ai-providers#configuring-credentials).

<Note>
  For details on which models each provider supports and how routing works, see [AI Providers](/ai-providers).
</Note>

## Running the gateway standalone

Mission Control spawns and manages the gateway for you. To run it on its own — for a headless server or Docker — start it directly:

```bash
npm run gateway
```

It uses `~/.dash/gateway` for its data and creates agents, channels, and credentials through its [Management API](/api-reference). The gateway accepts these flags:

| Flag | Description |
|------|-------------|
| `--management-port <port>` | Port for the Management API (default: `9300`). |
| `--channel-port <port>` | Port for the WebSocket channel server (default: `9200`). |
| `--token <token>` | Bearer token required on the Management API. |
| `--chat-token <token>` | Token required on the channel server (`ws://…/ws/chat?token=…`). |
| `--data-dir <path>` | Override the gateway's data directory (default: `~/.dash/gateway`). |
| `--verbose` | Enable debug logging. |

There are no `--config` or `--secrets` flags, and the gateway does not read any JSON config file — agents, channels, and credentials are managed at runtime through the [Management API](/api-reference), which is exactly what Mission Control uses.

## Remote gateway runtime

Mission Control can also use a gateway that runs somewhere else, such as a VPS.
Open **Settings → General → Gateway** to choose where MC should connect.

**Local gateway** is the default. Mission Control starts the gateway on this
machine and talks to it over loopback.

**Relay or hosted endpoint** connects Mission Control to an existing gateway URL.
Enter the management URL, chat URL, management token, chat token, and relay
credential if your relay requires one. The URLs are saved in Mission Control's
settings. Tokens and relay credentials stay in the OS keychain.

**Deploy to VPS** connects over SSH, installs Dash on the server, creates a
`dash-gateway` systemd user service, starts the gateway with your relay settings,
and then saves the resulting relay endpoint in Mission Control. You need a VPS
that already has Node.js, npm, git, and systemd user services available.

<Note>
  A hosted Dash gateway will use the same endpoint shape: a management URL, chat
  URL, and gateway tokens. The current flow can connect to one once those details
  are issued, but it does not create hosted gateways for you yet.
</Note>

## Credentials

Provider API keys and messaging tokens are encrypted at rest. The gateway keeps them in `~/.dash/gateway/credentials.enc` (AES-256-GCM); gateway access tokens live in your OS keychain. See [Secrets](/secrets) for the full picture of how credentials are stored and delivered to agents.

## Plugins

Plugins let you drop extra skills into any Dash agent without touching the config file. The gateway discovers plugins from the `plugins/` directory inside the **gateway's data directory** — that is, `~/.dash/gateway/plugins/`. Throughout this section, `<dataDir>` is shorthand for that gateway data directory (`~/.dash/gateway`), not Mission Control's `~/.dash/desktop`.

<Note>
For a step-by-step guide to discovering, enabling, trusting, and using plugins, see [Plugins](/plugins). This section is the detailed reference: directory layout, the `config.json` schema, hook events, and the provider catalog schema.
</Note>

### Directory layout

```
<dataDir>/                  # the gateway's data directory: ~/.dash/gateway
└── plugins/
    ├── config.json
    └── <plugin-name>/
        ├── .claude-plugin/
        │   └── plugin.json          (optional)
        ├── skills/
        │   └── <skill-name>/
        │       └── SKILL.md
        ├── commands/
        │   └── <command-name>.md    (optional)
        ├── agents/
        │   └── <agent-name>.md      (optional)
        ├── hooks/
        │   └── hooks.json           (optional, trusted only)
        ├── .mcp.json                (optional, trusted only)
        ├── providers/
        │   └── <provider>.json      (optional, trusted only)
        └── bin/                     (optional, trusted only)
            └── <executable>
```

Each plugin follows the Claude Code layout:

- **`skills/`** — one subdirectory per skill, each with a `SKILL.md` file in standard frontmatter format (`name`, `description`, body).
- **`commands/`** — flat `<name>.md` files. Each becomes a `/<plugin>:<command>` slash command (see below).
- **`agents/`** — flat `<name>.md` files (Claude Code subagent format). Each becomes a loadable specialist (see below).
- **`hooks/hooks.json`** — event hooks that run shell commands at key points in a run (see [Hooks](#hooks) below). Code execution, so it requires `trusted`.
- **`.mcp.json`** — extra MCP servers to register with the gateway. Code execution, so it requires `trusted` (see below).
- **`providers/`** — flat `<provider>.json` LLM provider catalogs that add selectable models. Credential-bearing, so they require `trusted` (see [LLM providers](#llm-providers) below).
- **`bin/`** — executables prepended to the gateway's `PATH`. Code execution, so it requires `trusted`.

The `.claude-plugin/plugin.json` manifest is optional; when present it can set `name`, `displayName`, `description`, and `version`. When absent, the plugin's directory name is used as its name.

### Enabling a plugin

Create or edit `<dataDir>/plugins/config.json`:

```json
{
  "<plugin-name>": { "enabled": true }
}
```

Plugins not listed in `config.json`, or listed with `"enabled": false`, are ignored.

### Trusting a plugin

`enabled` is enough for markdown components — `skills/` and `commands/`, which never run code. Components that **execute code or handle credentials** — `hooks/hooks.json`, `.mcp.json` servers, `bin/` executables, and `providers/` LLM catalogs — additionally require `"trusted": true`:

```json
{
  "<plugin-name>": { "enabled": true, "trusted": true }
}
```

An enabled-but-untrusted plugin still contributes its skills and commands, but its hooks, MCP servers, `bin/` directory, and provider catalogs are skipped. Only set `trusted` for plugins whose code you have reviewed and trust to run inside the gateway process.

### Loading a plugin from a path

A `config.json` entry can point at a plugin directory anywhere on disk with a `path` field, instead of requiring the plugin to live under `<dataDir>/plugins/`. This is handy for local development — you can keep a plugin in your own working tree and load it without copying it in:

```json
{
  "my-dev-plugin": { "path": "/abs/or/relative/dir", "trusted": true }
}
```

A `path` entry is **enabled automatically** — you do not need `"enabled": true`. It still requires `"trusted": true` to run code components (hooks, MCP servers, `bin/` executables, and provider catalogs); skills and commands load from `enabled` alone, just like any other plugin.

### Commands

Each `commands/<name>.md` file becomes a slash command named `/<plugin>:<name>`. For example, a plugin called `my-skills` with `commands/triage.md` exposes `/my-skills:triage`. The command body is the markdown content; optional frontmatter (`name`, `description`) overrides the command name and supplies a description. The slash name is `<plugin>:<frontmatter-name>` when `name:` frontmatter is present, otherwise `<plugin>:<filename-without-.md>`. Commands need only `enabled`.

### Subagents (specialists)

Each `agents/<name>.md` file (Claude Code subagent format — frontmatter `name`/`description` plus a markdown body) is exposed as a **loadable specialist**. For example, a plugin called `my-skills` with `agents/reviewer.md` is invocable as `/my-skills:reviewer` or via the agent's `load_skill` tool. As with commands, the loadable name is `<plugin>:<frontmatter-name>` when `name:` frontmatter is present, otherwise `<plugin>:<filename-without-.md>`. When loaded, the specialist contributes its instructions to the conversation on demand. Like commands, subagents are markdown — they need only `enabled` (not `trusted`).

**Loadable specialists run in the main session.** A loaded specialist contributes its instructions to the *current* conversation, so its `tools` frontmatter field is **advisory, not enforced** — the specialist uses the agent's own tool set. This is different from **isolated** subagents: for true parallel workers that each run in a **separate context** with a restricted tool subset, enable the agent's [**Swarm**](#swarm) feature and let it use the `spawn_worker` tool. See [Tools](/tools#swarm-orchestration).

### MCP servers and executables

A trusted plugin's `.mcp.json` is read at startup and its servers are registered with the gateway's MCP manager and persisted alongside your other MCP servers. Registration is fail-isolated: a server that fails to start is logged and skipped without affecting the rest of the gateway. A trusted plugin's `bin/` directory is prepended to the gateway's `PATH`, so its executables resolve ahead of system binaries.

### Hooks

A trusted plugin can register **hooks** — shell commands that run at key points in an agent run — via a `hooks/hooks.json` file in the [Claude Code hooks format](https://docs.claude.com/en/docs/claude-code/hooks). Hooks run shell commands, so they require `"trusted": true`; an untrusted plugin's hooks are skipped.

Supported events:

| Event | When it fires | What it can do |
| --- | --- | --- |
| `SessionStart` | Before the model runs, at the start of a run | Add context to the system prompt |
| `UserPromptSubmit` | After an inbound channel message passes routing, before the agent runs | Block the message, or prepend context to the prompt |
| `PreToolUse` | Before a tool executes (matched by tool name) | Allow or deny the tool call |
| `PostToolUse` | After a tool executes (matched by tool name) | Block the result, or append context |
| `Stop` | After the run completes | Cleanup (its output is logged, not injected) |
| `SubagentStart` | When an [agent swarm](/tools#swarm-orchestration) worker starts (matched by worker role) | Observe worker starts — log, notify, audit |
| `SubagentStop` | When a swarm worker finishes, fails, or is cancelled (matched by worker role) | Observe worker results — log, notify, audit |

Each event maps to an array of matcher groups; each group has an optional `matcher` (a tool name, a `|`-separated list, or a regex — omit or use `*` to match everything) and a `hooks` array of `{ "type": "command", "command": "...", "timeout": <seconds> }` entries.

```json
{
  "PreToolUse": [
    {
      "matcher": "bash",
      "hooks": [
        { "type": "command", "command": "${CLAUDE_PLUGIN_ROOT}/scripts/guard.sh" }
      ]
    }
  ],
  "UserPromptSubmit": [
    {
      "hooks": [
        { "type": "command", "command": "${CLAUDE_PLUGIN_ROOT}/scripts/inject-context.sh" }
      ]
    }
  ]
}
```

Hook commands receive the Claude Code event payload (`tool_name`, `tool_input`, `prompt`, `session_id`, `cwd`, …) as JSON on **stdin**, and communicate back through their exit code and stdout:

- **Exit `0`** — allowed. To deny, add context, or replace tool input, print a JSON object with a `hookSpecificOutput` field (e.g. `{"hookSpecificOutput":{"permissionDecision":"deny","permissionDecisionReason":"..."}}` or `{"hookSpecificOutput":{"additionalContext":"..."}}`).
- **Exit `2`** — blocking error. Standard error becomes the block reason.

The string `${CLAUDE_PLUGIN_ROOT}` in a command is substituted with the plugin's absolute directory, so hooks can reference scripts bundled with the plugin. `${CLAUDE_PROJECT_DIR}` and `${CLAUDE_PLUGIN_DATA}` (a per-plugin scratch directory) are also available.

**Fail-open by design.** A hook that errors, times out, exits non-zero (other than `2`), or prints malformed JSON is ignored — the run proceeds as if the hook had allowed it. Hooks never crash the gateway.

**Where each event fires.** `SessionStart`, `PreToolUse`, `PostToolUse`, and `Stop` fire on **every** agent run, whether the run was reached through Mission Control chat or an inbound channel. `UserPromptSubmit` fires **only on the channel path** (Telegram, WhatsApp); it does not run for Mission Control chat messages. `SubagentStart` and `SubagentStop` fire only for swarm-enabled agents, around each worker's lifecycle; their stdin payload carries `worker_id`, `role`, and (on stop) the terminal `status` (`done`, `failed`, or `cancelled`). They are observe-only — a Subagent hook cannot block a worker, and its output is logged, not injected.

### LLM providers

A trusted plugin can add a whole **LLM provider** — a base URL, a wire protocol, and a list of models — through one or more `providers/<provider>.json` catalog files. Once loaded, its models appear in Mission Control's model dropdown as `<id>/<model-id>` and any agent can be pointed at them, exactly like the built-in providers.

<Warning>
  A provider catalog requires `"trusted": true`. A provider sees **every prompt** you send to its models, **receives your API key**, and **chooses the network endpoint** requests go to. Only add provider plugins you trust with all three.
</Warning>

Each catalog file is a single JSON object:

```json
{
  "id": "myllm",
  "label": "My LLM",
  "credentialPrefix": "myllm-api-key",
  "baseUrl": "https://api.myllm.example/v1",
  "api": "openai-completions",
  "models": [
    {
      "id": "my-fast",
      "name": "My Fast",
      "contextWindow": 128000,
      "maxTokens": 8192,
      "reasoning": false,
      "cost": { "input": 0.5, "output": 1.5, "cacheRead": 0, "cacheWrite": 0 }
    }
  ]
}
```

| Field | Required | Description |
| --- | --- | --- |
| `id` | yes | Provider id and the `<id>/<model>` prefix. Also the credential lookup name. |
| `label` | yes | Human-readable provider name. |
| `baseUrl` | yes | API base URL the gateway calls. |
| `api` | yes | Wire protocol: `openai-completions` or `anthropic-messages`. |
| `credentialPrefix` | yes | Prefix the API key is stored under (e.g. `myllm-api-key`). |
| `models[]` | yes | Statically-known models. Each needs `id`, `contextWindow`, `maxTokens`; `name`, `reasoning`, `cost`, `input`, `headers`, and `compat` are optional. |
| `dynamicModels` | no | OpenRouter-style "accept any model id" — see below. |
| `dynamicModelDefaults` | no | `{ "contextWindow", "maxTokens" }` applied to dynamically-accepted ids. |
| `placeholderKey` | no | Stand-in key for keyless local servers — see below. |

**Storing the API key.** Save it in the credential store under `<id>-api-key:<name>`, for example `myllm-api-key:default`. The simplest way is Mission Control's **Settings → AI Providers** screen, which writes that key for you; you can also set it directly with the gateway's credentials API. The first key stored for a provider id wins.

**Accept-any-model providers.** Set `"dynamicModels": true` together with `"dynamicModelDefaults": { "contextWindow": ..., "maxTokens": ... }` to allow any model id the provider supports — useful for aggregators like OpenRouter where the catalog can't list everything. Listed `models` still appear in the dropdown; an unlisted id is accepted on demand and sized from the defaults. (Without `dynamicModelDefaults`, an unlisted id is rejected — the gateway can't size it.)

**Keyless local servers.** For a local server that needs no real key (such as Ollama), set `"placeholderKey": "ollama"` (any non-empty string). The gateway uses it whenever no real key is stored, so the provider authenticates out of the box.

If you already run an OpenAI- or Anthropic-compatible endpoint (OpenRouter, OpenClaw, a self-hosted gateway, …), porting it is just filling in this catalog — `baseUrl`, `api`, and the model list.

### Example

```bash
# Create the plugin directory and a skill
mkdir -p /path/to/data/plugins/my-skills/skills/summarize

cat > /path/to/data/plugins/my-skills/skills/summarize/SKILL.md <<'EOF'
---
name: summarize
description: Summarize any text concisely
---
Summarize the provided text in three sentences or fewer.
EOF

# Enable the plugin
echo '{ "my-skills": { "enabled": true } }' \
  > /path/to/data/plugins/config.json
```

When the gateway starts, it logs `[plugins] loaded 'my-skills' (skills)` and the agent's `load_skill` tool (see [Tools](/tools) — requires `load_skill` in the agent's tools list) can reference any skill from that plugin.

<Note>
  Skills, commands, subagents, hooks, MCP servers, `bin/` executables, and LLM providers are active. Plugin subagents load into the main session (see above). For **isolated** parallel workers — each with its own context and tool subset — enable the agent's [Swarm](#swarm) feature.
</Note>
